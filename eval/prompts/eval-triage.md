## やること

### 1. 未検出の原因診断

`eval/runs/<ラウンドID>.json` と成果物を読み、**未検出だった項目ごとに**、次のどれに当たるかを判定してください。推測で埋めず、成果物のどこを見てそう判断したかを引用すること。

| 原因区分 | 意味 |
|---|---|
| 手順の欠落 | SKILL.md の手順にその観点を見る指示が無い |
| 参照ナレッジの欠落 | チェックリスト・カタログにその型が載っていない |
| 前段の情報落ち | 前の成果物では捉えていたのに後段で落ちた(バケツリレーの断絶) |
| モードの限界 | そのモードでは原理的に出ない(限界の宣言どおり。**改善対象ではない**) |
| 資料の限界 | 資料に手掛かりが無く、proposed としてしか出せない(改善対象ではないが、資料要求として運用フィードバックに書く) |
| 説明不能 | 上のどれでもない。次ラウンドの調査対象として残す |

**「モードの限界」「資料の限界」に倒しすぎないこと。** 難易度Cの項目は資料の限界に見えやすいが、`business-scenario-patterns.md` に型があれば拾えるものが混ざっています。

### 2. 誤指摘の分析

人が「誤指摘」と仕分けたエントリについて、**何を読み違えたか**を特定してください。件数ではなく原因の型(資料の読み飛ばし / 別文書との混同 / 一般論の当てはめ)で分類します。

### 3. 改善提案

診断結果を、対象ファイル別の改善提案にまとめてください。書式は qa-improvement 手順5(きっかけ / 発生頻度 / 変更内容 / 期待効果)に従います。

- **答えキーの文言をそのままスキルに書かない。** それは改善ではなく答えの埋め込みです。一般化できる「型」に落ちないものは提案にしないでください。
- 過去の `eval/runs/*.json` と `maintenance-log.md` を読み、**同趣旨の提案が既出か**を必ず添えます。

### 4. トリアージ

[maintenance-log.md](../../.github/skills/_shared/maintenance-log.md) のトリアージ手順に従い、項目ごとに「要約 / 根拠 / 出現頻度 / 過去履歴 / 推奨」を提示し、**選択式(採用 / 修正して採用 / 保留 / 見送り)で採否を聞いてください**。一括反映はしないこと。

### 5. 反映と記録

採否が決まったら:

1. 採用分をマスターへ反映する(構成が変わる変更は skill-map.md §5 の手順に従う)
2. `maintenance-log.md` に**全項目の判断を理由付きで**追記する(見送り・保留も残す)
3. 次ラウンドで確認すべきことを1〜3行でまとめる(どの未検出項目が拾えるようになるはずか)

### 6. 答えキーの更新(該当する場合のみ)

人が「キーの漏れ」と仕分けたエントリがあれば、`eval/answer-key/prq/*.csv` に追記してください。

- `rationale` に**資料上の根拠**(ファイル名と節)を必ず書く。根拠を書けないものはキーにしない
- 追記したら `eval/runs/runs.csv` の当該ランの `note` に「キー追加 N件」と記録する(母数が変わるため、以後の比較の前提が変わる)
