# 評価用フィクスチャ: 購買申請システム(PRQ)

架空の企業・架空のシステムの設計資料一式。**スキルセットの評価ラン([eval/README.md](../../README.md))の入力**であり、実在の企業・製品とは関係ない。PoC やデモの題材としてもそのまま使える。

## 題材

株式会社カナメ製作所(製造業・従業員1,200名)の購買申請システム PRQ。紙とExcelで回している購買依頼を電子化する刷新プロジェクトの、要件定義〜基本設計フェーズを想定している。

ルート README の「業務シナリオ設計を試す」が挙げる条件をすべて満たすように作ってある。

| 条件 | この題材での該当 |
|---|---|
| 2〜3ロールが関与する | 申請者・承認者・上位承認者・購買担当・経理担当の5ロール |
| 主要オブジェクトに4状態以上ある | 申請が9状態(下書き/承認待ち/差戻し/承認済み/発注済み/検収済み/計上済み/取消/失効) |
| 申請・承認・差戻し・取消がある | すべてある。二段階承認と自動失効も含む |
| 外部システムまたはバッチ連携が1つある | 会計システム連携・EDI発注送信・人事マスタ同期・月次締めの4バッチ |
| DBまたはAPIで業務結果を確認できる | テーブル定義書があり、状態・承認履歴・監査ログを業務オラクルにできる |

## 資料の性格(意図的に作り込んである点)

- **文書間に矛盾がある。** 単一の文書を読むだけでは気づかず、読み比べて初めて分かるものを含む。
- **決まっていないことがある。** 業務を最後まで追うと必ずぶつかるのに、どの文書にも書かれていない事項がある。
- **運用手順書は現行運用の記述であり、PRQ の仕様ではない。** ここに書かれた運用をシステム仕様として扱うと誤指摘になる。暗黙知の手掛かりとしては有効。
- **ノイズが混ぜてある。** 対象外の記述・過去の経緯・関係の薄い運用が入っており、資料の充足度フィードバックの材料になる。

**矛盾や欠落は仕込みであって、修正対象ではない。** 資料を直すと答えキーが合わなくなる。

## 使うとき

評価ランとして回すなら [eval/prompts/eval-run.md](../../prompts/eval-run.md) をそのまま使う。単に試したいだけなら、`qa-orchestrator` にこのディレクトリを入力として渡せばよい。

いずれの場合も **[eval/answer-key/](../../answer-key/) を一緒に読ませないこと**(答えを見せた結果は測定にならない)。
