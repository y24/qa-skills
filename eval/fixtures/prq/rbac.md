## 1. ロール定義

| ロールID | ロール名 | 付与対象 | 付与方法 |
|---|---|---|---|
| `REQUESTER` | 申請者 | 全社員 | 全ユーザーに既定で付与 |
| `APPROVER` | 承認者 | 部門長 | 人事マスタの役職から日次で自動付与 |
| `SENIOR_APPROVER` | 上位承認者 | 調達部長 | 手動付与 |
| `BUYER` | 購買担当 | 調達部員 | 手動付与 |
| `ACCOUNTANT` | 経理担当 | 経理部員 | 手動付与 |
| `ADMIN` | システム管理者 | 情報システム部員 | 手動付与 |

1人のユーザーが複数のロールを持つことがある(例: 調達部長は `APPROVER` と `SENIOR_APPROVER` を持つ)。

## 3. 部門スコープ

- `APPROVER` の「自部門」は、人事マスタ上で当該ユーザーが部門長として登録されている部門を指す。
- 兼務により複数部門の部門長である場合、いずれの部門の申請も承認できる。
- 部門は階層を持たない(フラットな12部門)。上位部門による代理承認は行わない。

## 4. 権限制御の実装方針

- 画面は、権限のない操作のボタンを非表示にする(NFR-04)。
- APIは、画面表示の有無にかかわらずサーバ側で権限を検証する。検証に失敗した場合は 403 を返し、監査ログに `permission_denied` として記録する。
- 参照系APIは、部門スコープを SQL の WHERE 句で強制する(アプリ層のフィルタに依存しない)。

## 5. 監査ログの記録対象

| イベント | 記録項目 |
|---|---|
| 状態変化 | 申請ID・遷移前後の状態・操作者・日時 |
| 承認・差戻し | 申請ID・ステップ・操作者・代理フラグ・コメント・日時 |
| 権限エラー | 操作者・要求API・対象申請ID・日時 |
| マスタ変更 | 対象マスタ・変更前後の値・操作者・日時 |
