# スキルセットの改善ループ(評価ラン)

このスキルセットが**実際に効いているか**を測り、改善を積み上げるための仕組み。**このファイルがループの定義元**で、プロンプト・答えキー・スクリプトはここに従う。

`eval/` はメンテナー側の資産であり、**配布されるスキルセット(`.github/skills/`)には含まれない**。利用側プロジェクトへコピーする必要はない。

## 0. 前提 — 自動実行はしない

**AIエージェントの自律実行・時間トリガーでの定期実行は行わない。** ループは必ず人が起動する。ここでの設計目標は「人を減らす」ことではなく、**1回のトリガーで取れる情報を最大化し、人の判断を必要な場所だけに残す**ことにある。

| 誰が | 何をするか |
|---|---|
| **人** | ラウンドの起動(プロンプトを貼る)/ 未照合エントリの仕分け / 改善提案の採否 |
| **AI** | フローの実行 / 成果物の作成 / 採点の実行 / 診断と改善提案の作成 / 採用分の反映 |
| **機械(スクリプト・hooks・CI)** | 答えキーとの照合 / 指標算出 / 書式とトレースの検証 / 記録 |

hooks は**検証しかしない**。ランを起動する hook・スケジューラは置かない(定義元: [_shared/hooks.md](../.github/skills/_shared/hooks.md))。

## 1. 何を測るのか

「良い成果物だったか」は機械では測れない。測れるのは **仕込んだものを拾えたか** だけである。

そこで、架空の業務システム([fixtures/prq/](fixtures/prq/))に**意図的な仕様の矛盾・欠落・暗黙知**を仕込み、正解を[answer-key/prq/](answer-key/prq/)に持たせた。評価ランの成果物をこのキーと突き合わせれば、検出率は決定論的に出る。CI の `verifier-selftest`(欠陥を仕込んで検証層が気づくかを見る)と同じ考え方を、**スキルの出力層へ広げたもの**である。

| 測るもの | 方法 | 測らないもの |
|---|---|---|
| 仕込んだ項目の検出率(難易度A/B/C別) | 答えキー照合(機械) | 指摘の**妥当性**(キーに無い指摘が正しいか) |
| 根拠なし事実主張率・トレース率・カバレッジ | `metrics.py`(機械) | 成果物の**読みやすさ・使いやすさ** |
| ループバック回数・改善メモ件数 | `qa-session.json`(機械) | 実務での**採用率・修正量** |

**誤指摘率は自動判定しない。** 答えキーに当たらなかった指摘は「未照合エントリ」として列挙されるだけで、誤指摘なのかキーの漏れなのかは人が仕分ける(§5)。誤検出しない検査だけを機械の判定に使うという原則([設計原則11](../README.md))はここでも同じ。

## 2. 1周の流れ

```
  [人] eval-run.md を貼る
        ↓
  [AI] Process モードでフルフローを実行(ゲートは §3 の台本で自己承認)
        ↓  qa-output/eval-prq-<ラウンド>/ に成果物 + 90-improvement.md
  [AI] eval_score.py score を実行 → 採点表 + ラン台帳に1行追記
        ↓
  [人] 採点表の「未照合エントリ」だけを見て仕分ける(5〜10分)
        ↓
  [人] eval-triage.md を貼る
        ↓
  [AI] 未検出の原因診断 → 改善提案 → maintenance-log.md のトリアージ形式で選択式に提示
        ↓
  [人] 採否を選ぶ(選択式)
        ↓
  [AI] 採用分をマスターへ反映し、maintenance-log.md に履歴を残す
        ↓
  次ラウンドへ(同じフィクスチャで再ラン → compare で効果を確認)
```

人が触るのは**メッセージ2通と選択回答だけ**で、それ以外は自動で進む。

### コマンド早見表

```bash
python eval/scripts/eval_score.py score qa-output/eval-prq-01 --key eval/answer-key/prq --run-id 01 --model <モデル名> --append eval/runs/runs.csv --out eval/runs/01.json
```

```bash
python eval/scripts/eval_score.py compare eval/runs/runs.csv --baseline 01 --target 02
```

```bash
python eval/scripts/eval_score.py selftest
```

## 3. 評価ランのゲート応答(台本)

通常運用ではゲートで人が承認する(conventions.md §4)。評価ランでは、人の都合でループが止まらないよう、**プロンプトで事前に承認方針を与え、AIが台本に従って自己承認する**。台本の本文は [prompts/eval-run.md](prompts/eval-run.md) にあり、要点は次のとおり。

- G1〜G5 は台本の判断基準に従って承認して進む。承認した内容の要約は成果物とセッションに残す。**承認は自動でも、レビュー依頼(gates.md §4-1)は組み立てて出力に残す** — ゲートで人に何を見せるかを評価するため。
- **聞かずに、聞くはずだった質問を記録する。** 自己承認は「対話の質」の観測を消してしまうため、AIは実際には質問せず、**選択肢まで組み立てた質問を `improvement_notes` に残す**。ここが後で「質問が多すぎ/少なすぎ/選択肢が不適切」の材料になる。
- セッション名は `eval-` で始める。`decisions` に「評価ランの事前承認による」と記録する。

**評価ランの成果物を実務の成果物として使ってはならない。** 人が承認していないため、conventions.md §4 の「人間が承認したもの」の要件を満たさない。

## 4. 答えキーを見せない

`eval/answer-key/` を評価ランの入力に含めない。答えを見せて解かせた結果は検出率としての意味を持たない。

`eval_score.py` は `qa-session.json` の `inputs` に答えキーのパスが含まれていたら**採点を無効(exit 3)にする**。ただしこれは事故の検出であって防止ではない — 実行するAIに答えキーを読ませない運用は人が守る。

## 5. 未照合エントリの仕分け(人がやる唯一の読み仕事)

採点表の §2 に、答えキーのどれにも当たらなかった指摘・項目が並ぶ。ここだけを人が見る。

| 仕分け | 意味 | 次のアクション |
|---|---|---|
| **誤指摘** | 資料を読み違えている。存在しない矛盾を挙げた | 改善提案の材料にする(検出精度の劣化。狼少年化の兆候) |
| **キーの漏れ** | 妥当な指摘だが答えキーに無い | **答えキーに追加する**(§6) |
| **粒度違い** | キーの項目を別の切り口で言っている | キーの `match` に別表記を足す |

誤指摘率だけを下げるなら検出をやめれば達成できてしまうので、**検出率と対で見る**(qa-improvement の敵対的ペアと同じ考え方)。

## 6. 答えキーの育て方

- 追加するのは「仕込んだつもりはないが、資料から確かに導ける」項目。**資料に根拠がないものをキーにしない。**
- `match` は**別表記に寛容・語の組み合わせに厳しく**書く。1グループ(`;`区切り)ずつ必要で、グループ内は別表記(`|`区切り)。照合前に全角/半角・大文字小文字・空白・カンマは吸収される。
- キーを増減したら **run_id と一緒に `runs.csv` の `note` に記録する**。母数が変わると検出率は前後のランと比較できない(§7)。

## 7. ばらつきと採否の基準(ラチェット)

生成はばらつく。**1回のランの差分で採否を決めない。**

| 判定 | 目安 |
|---|---|
| 改善とみなす | 同一条件(同じフィクスチャ・モデル・モード・答えキー)で**2ラン以上**、全体検出率が **+5pt 以上** |
| 横ばい | 差が ±5pt 未満。採用しても構わないが「効果あり」とは記録しない |
| 悪化 | −5pt 以上。**変更を戻す**(スキル側の変更を revert し、maintenance-log に理由を残す) |

- 難易度C(暗黙知)は母数が小さい。1件の増減で率が大きく動くので、**件数で読む**。
- モデルを変えたランは比較対象にしない。`runs.csv` の `model` 列が違うランの差分は無意味。

## 8. マスターへの反映は既存の経路を通す

改善は**必ず** [maintenance-log.md](../.github/skills/_shared/maintenance-log.md) のトリアージを経る。評価ランだからといって直接スキルを書き換えない。1セッション(1ラン)の特殊事情を一般ルール化してしまう歯止めが、あの履歴だけだからである(conventions.md §8)。

評価ランの 90-improvement.md も、実案件の 90-improvement.md と**同じ棚に乗せて**まとめて検討する。評価ランだけを見て採否を決めると、フィクスチャに最適化された変更が通ってしまう。

## 9. 失敗モード

| 失敗 | 兆候 | 対策 |
|---|---|---|
| **フィクスチャへの過学習** | 検出率だけが上がり、実案件の手応えが変わらない | 答えキーの文言をスキルに書かない。フィクスチャを2本目・3本目と増やし、**1本は改善に使わず検証専用に温存する** |
| **答え合わせの形骸化** | 未照合エントリを毎回「キーの漏れ」に倒す | 追加は「資料に根拠がある」ものだけ。キー追加時は理由を `rationale` に必ず書く |
| **採点の劣化** | 検出率が理由なく上がる | `eval_score.py selftest` を CI で毎回回す(検証層自身の自己検査と同じ) |
| **比較の混線** | モデル・キー・モードが違うランを比べる | `runs.csv` の条件列を必ず埋める。`compare` は条件を併記する |

## 10. 構成

```
eval/
  README.md                  # ★このファイル(ループの定義元)
  prompts/
    eval-run.md              # ラウンド起動用。人が貼る1通目(ゲート応答の台本を含む)
    eval-triage.md           # 診断・トリアージ用。人が貼る2通目
  fixtures/prq/              # 架空の業務システム(購買申請システム PRQ)の入力資料一式
  answer-key/prq/            # ★答えキー(仕込んだ項目の正解)。ランに読ませない
  scripts/
    eval_score.py            # 採点・ラン台帳追記・ラン比較・自己検査
  runs/
    runs.csv                 # ラン台帳(1ラン=1行)。追記のみ
    <run-id>.json            # 各ランの採点結果(明細付き)
```

**依存の向きは `eval/` → `.github/skills/` の一方向。** 配布されるスキルセットの側から評価ハーネスを参照しない(参照すると配布先でリンク切れになり、外側から検証するという前提も崩れる)。CI も分けてある — スキルセットの検証は `qa-artifacts.yml`、採点ハーネスの自己検査は `eval-harness.yml`。

評価ランのセッション(`qa-output/eval-prq-*/`)を commit するかは任意。commit すれば CI の `qa-artifacts` ジョブが成果物のゲート検証を掛けるので、**採点とは別の観点(書式・トレース・スキーマ)で**そのランを検査できる。

## 11. 最初の1周

1. `python eval/scripts/eval_score.py selftest` が通ることを確認する
2. [prompts/eval-run.md](prompts/eval-run.md) をそのまま貼る(ラウンドIDだけ書き換える)
3. 出てきた採点表の §2 を仕分ける
4. [prompts/eval-triage.md](prompts/eval-triage.md) を貼り、採否を選ぶ
5. 2に戻る

1周目の検出率は**ベースライン**であって成績ではない。低くても改善の余地が見えているだけで、それがこの仕組みの目的である。
